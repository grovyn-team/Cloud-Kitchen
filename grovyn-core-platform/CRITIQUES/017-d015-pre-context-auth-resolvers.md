# CRITIQUE 017 — D-015 / P1-02 S1: pre-context auth read path (SECURITY DEFINER resolver functions)

**Verdict: ENDORSE WITH CHANGES (Significant). Critic gate on D-015 SATISFIED — it may move to Accepted.** The mechanism is correct, the footgun the whole design hinges on (`SECURITY DEFINER` search-path hijack) is genuinely closed and genuinely tested, and the choice over the narrow-role alternative is right for a real reason, not a lazy one. Two non-optional forward specs (both on *unbuilt* tasks, neither an edit to `0002`): a user-enumeration **timing** side channel that P1-04 must close, and a function-owner/definer assertion P1-10 must add. Neither blocks S2 or S3 of P1-02.

**Self-review flag — louder than usual this time.** D-015 chose one of the *two options I myself named* in CRITIQUE 016 §C.1 ("a narrow SELECT-only `grovyn_auth` role; or `SECURITY DEFINER` resolver functions"). This is my own recommendation coming back to me, which is the single easiest place for this review to become a rubber stamp — I proposed the menu, the DBA picked from it, and agreeing with myself costs nothing. So I pressed hardest exactly where my CRITIQUE 016 framing was thinnest: (1) I did not, in 016, think through the *timing* consequences of the read path — and that is where the real unowned gap is (§5, §C.1); (2) I asserted `SECURITY DEFINER` resolvers "add nothing irreversible" without checking the search-path semantics — so I checked them here against Postgres behaviour rather than trusting that a passing test means the right thing passed (§B.1).

---

## 1. The decision, restated

Stated: "pick `SECURITY DEFINER` functions over a narrow role for the pre-context auth read path." What is *actually* being decided is narrower and more durable than that framing: **this is the permanent shape of the only sanctioned hole in the fail-closed wall.** P1-00/P1-01 built and verified that `grovyn_app` reads zero rows with no context set. Login structurally cannot honour that (you must find the tenant and user *before* you have a tenant context). So *something* has to be allowed to read `tenant`/`user` unscoped, and D-015 decides what that something is and how tightly it is bounded. The right question is not "functions vs role" but "what is the blast radius of the exception, and does it stay that small as the product grows." Judged on that axis, the design is good.

## 2. Goal alignment

Direct and honest. This is O4 (Trust it — tenant isolation stays fail-closed for every path *except* two named, bounded, audited ones) and it unblocks O1/O2 by making login physically possible at all. It also serves O4 in the subtle way that matters: it does *not* solve the pre-context problem by widening the general query surface (the rejected third option — a permissive `SELECT` policy for `grovyn_app`), which would have dissolved the very guarantee P1-00 spent a spike proving. Choosing the mechanism that keeps every *other* path fail-closed is the outcome-aligned call. No part of `0002` traces to nothing.

## 3. Strongest case for

It is the minimum-blast-radius option. A `SECURITY DEFINER` function is a *fixed* capability: fixed parameters, fixed return columns, fixed `WHERE`. A SQL-injected or compromised `grovyn_app` call site cannot turn `authenticate_lookup` into `SELECT * FROM "user"` — it gets at most one row per call, by exact email, within one tenant. Contrast the rejected `grovyn_auth` role holding blanket (even column-limited) `SELECT` on `tenant`/`user`: behind that role, injection *is* an unscoped dump of every tenant's user list. The function also baked the two easy-to-get-wrong correctness rules from CRITIQUE 016 §B.4 (`deleted_at IS NULL`, case-insensitive `lower(email)` matching the partial unique index's exact shape) into a single chokepoint instead of leaving them to per-call-site P1-04 code. And it went past inspection: the search-path hijack test planted a *working* poison (an ordinary unqualified query in the same session picked up the rogue `evil.tenant` row) and showed the function still returned the real row — that is a real differential test, not a green checkmark.

## 4. Strongest case against

Two lines of attack, both survivable, one requiring a mandatory follow-up.

- **The read path is a user-enumeration oracle, and D-015 is silent on it (§5).** The function correctly returns 0 rows for a missing/soft-deleted user and a full row (incl. `password_hash`) for a present one. That asymmetry, once wired into P1-04, becomes a *timing* oracle: a missing user returns fast (nothing to verify), a present user triggers an expensive argon2id verification app-side (slow). An attacker who knows a slug (slugs are public subdomains) can enumerate valid staff emails by response time. This is not a defect *in the function* — a read lookup cannot and should not perform argon2id itself — but it is a real consequence of this shape that nobody has assigned an owner, exactly the failure mode CRITIQUE 016 §C.1 was about (correct isolation, unowned capability).
- **`SECURITY DEFINER` is a known footgun *class*; a role is not.** The honest case for the rejected `grovyn_auth` role is that a `SELECT`-only role has no search-path attack surface at all and is inspectable with a stock `\dp`, whereas every `SECURITY DEFINER` function is a small standing liability that every future reviewer must re-audit for search-path/qualification hygiene. That case is real. It loses (below), but it is not a strawman and D-015's own alternatives analysis under-weights it slightly by framing the role purely on blast radius.

## 5. The cost nobody mentioned

**The timing/enumeration oracle is the cost, and it is a genuine forward liability, not a today-defect.** `authenticate_lookup` returning `password_hash` to the app layer is correct (argon2id verification must happen in Node; pgcrypto has no argon2id — doing it in-function is not a real option). But "return the hash, verify app-side" is precisely the pattern that leaks timing unless P1-04 performs a **dummy constant-time verify against a fixed decoy hash on the not-found path** and returns an identical error for "no tenant" / "no user" / "wrong password". None of that is written down anywhere — not in D-015, not on the P1-04 row. Left untracked, it ships as a working login that quietly enumerates every tenant's staff roster, and it will be found in a pen-test, not a code review, because every unit test will pass. This is the same species of finding as 016 §C.1: the mechanism is right, the *consequence* is unowned.

Secondary, minor: `resolve_tenant_by_slug` returns `name`, making it a tenant-existence-and-branding oracle for any probed slug. Acceptable — the slug is already a public subdomain and the name is shown on the login page — but it means unauthenticated slug probing is a sanctioned capability; rate-limit it at the edge (P1-04/gateway) rather than pretend it is private.

## 6. Reversibility

**Two-way door.** This is the class of thing CRITIQUE 016 explicitly said "sits on top of exactly these tables and adds nothing irreversible." Confirmed: `0002` creates two functions and moves two grants; it touches no table, no policy, no data, no column. Dropping or reshaping these functions later is a one-line migration. No tenant data lands here. The *only* thing with any stickiness is that P1-04 will be written to call these signatures — a code coupling, not a data one, and cheap to re-point. Do not agonise over it; the reason to get it right now is not reversibility, it is that it is the sanctioned exception to a one-way-door isolation model and therefore deserves the scrutiny, which it has had.

## 7. What would have to be true for this to be wrong

1. **That `SET search_path = ''` fully closes the hijack** (the user's explicit question 1). Checked against Postgres semantics, not just the passing test: `pg_catalog` is *always* implicitly searched first even when the path is empty, so built-in operators/types/`lower()` still resolve; `pg_temp` is never searched for functions or operators, and is only ever implicitly searched for *relation/type* names — of which the function bodies contain **none** unqualified (`public.tenant`, `public."user"`, `public.user_role` are all schema-qualified; `uuid`/`text` are pg_catalog built-ins). So `''` is not merely adequate, it is the modern *recommended* form, and it is strictly safer than `SET search_path = pg_catalog` would be (naming `pg_catalog` explicitly is redundant, and any non-empty user-schema entry would reopen the hole). The DBA got this exactly right; the empirical hijack test corroborates the semantic reasoning rather than substituting for it. **This assumption holds.**
2. **That the functions have no injection surface** (user's request). Confirmed by reading the bodies: `LANGUAGE sql`, static text, typed parameters (`text`/`uuid`) substituted as *values*. No `format()`, no `EXECUTE`, no string concatenation, no dynamic identifier. There is nothing to inject into. **Holds.**
3. **That the function owner is actually `grovyn_migrator` (BYPASSRLS) in every environment.** True *if* migrations run under `DATABASE_MIGRATOR_URL` (confirmed the config reads it). But if a migration is ever run as a superuser/`postgres` instead, the owner — and thus the definer identity — silently changes. Still functionally works (superuser also bypasses RLS), but it is unasserted ownership drift on the security-critical hinge. **Checkable — and P1-10 should assert it (change 2 below).**
4. **That P1-04 equalises the not-found vs wrong-password paths.** Currently *nothing* guarantees this. **Unverified and the reason for change 1.**

## B. Direct answers to the five pressure-test questions

**B.1 — Is `SECURITY DEFINER` + `search_path=''` + revoke-from-PUBLIC sufficient, or does it need `pg_catalog`?** Sufficient, and `''` is the correct choice — see §7.1. The three legs are each load-bearing and all present: (a) `search_path=''` + full qualification kills the hijack; (b) `REVOKE ALL ... FROM PUBLIC` then `GRANT EXECUTE ... TO grovyn_app` stops a future cluster role silently inheriting the path (verified in the SQL, lines 77–78, 122–123); (c) the function body's own `WHERE` is the actual scope, since RLS does not apply inside a definer body owned by a BYPASSRLS role. No known `SECURITY DEFINER` footgun is left open: search-path (closed), `PUBLIC` default grant (revoked), mutable-function injection (N/A, `STABLE` pure SQL). This is a textbook-correct hardened definer function.

**B.2 — Does the function leak more than it should? Password-hash return? Enumeration side channel?** Column selection is tight and correct — `resolve_tenant_by_slug` deliberately omits `plan`/`branch_limit`/`seat_limit`/timestamps (returns only `id`/`name`/`slug`); `authenticate_lookup` returns only login-relevant columns. Returning `password_hash` to the app layer is the *right* call, not a leak (argon2id must verify in Node; the hash is not the secret and only `grovyn_app` can `EXECUTE`). The real issue is not *what* the row contains but the *presence/absence timing* between "found" and "not found" — that is the §5 oracle, and it is a P1-04 obligation the function shape creates but cannot itself fix. Flagged as non-optional change 1.

**B.3 — Was option (a), the narrow role, genuinely inferior, or rationalised toward less work?** Genuinely inferior, and the evidence is that the chosen path was *more* work, not less: the DBA had to lock `search_path`, fully qualify every identifier, revoke from `PUBLIC`, and write a bespoke hijack test — a `SELECT`-only role needs none of that. If anything the lazy choice was option (a). Steelmanning (a) once more: it has zero definer footgun surface and is stock-inspectable — a real advantage. But it loses on the axis that matters here: blast radius under the realistic threat (app-layer SQLi/compromise), where a blanket `SELECT` role is a full cross-tenant user dump and the function is one-row-per-call by exact key. It also loses on operational fit — a distinct role needs a second pool/credential or mid-session `SET ROLE` (itself a footgun), whereas the function runs on `grovyn_app`'s existing connection. The reasoning in D-015's alternatives block is sound; I'd only sharpen that (a)'s auditability edge is real and the decision slightly under-credits it (§4).

**B.4 — Does this foreclose or complicate P1-04 or D-013?** No foreclosure, and it actively *helps* P1-04 by centralising the `deleted_at`/case-fold rules. Consistency with D-013/D-008 is clean: both functions filter `deleted_at IS NULL`, so a soft-deleted (churned) tenant and a terminated staff account both correctly fail login without a hard delete — exactly the soft-delete model D-013 chose. The one thing P1-04 must not do is route *around* these functions with a raw `SELECT` "because it returns zero rows" (D-015 consequence #1 already warns this) — and it must add the constant-time not-found path (change 1). The post-auth flow is unobstructed: once the tenant is resolved, P1-04 sets `app.current_tenant` and every subsequent query (session INSERT, audit INSERT) runs normally scoped.

**B.5 — Where did I press hardest against a choice I might have made myself?** On the search-path semantics (I verified `''` behaviour against Postgres rules rather than accepting the green test — §7.1), and on the enumeration timing (which my own CRITIQUE 016 §C.1 framing missed entirely — I named the read-path gap but not its timing consequence). Finding a real gap my prior framing created is the reason this is Endorse-*with-changes* and not a bare Endorse.

## C. What is NOT being built that should be tracked

- **P1-04:** constant-time not-found path + uniform auth error (§5) — **new, previously untracked.**
- **P1-10:** assert `pg_get_userbyid(proowner) = 'grovyn_migrator'` (or at least that the two functions are `SECURITY DEFINER`, owned by a BYPASSRLS role, and `EXECUTE`-granted to `grovyn_app` and nothing else) against the deployed cluster — extends 016 §B.2's `rolbypassrls=false` assertion to cover ownership drift on the definer hinge (§7.3). **New.**
- Already tracked, no action here: the `create_tenant()` write-path analogue (D-015 consequence #2, correctly deferred with self-serve onboarding); edge rate-limiting of slug probing (folds into P1-04/gateway).

## Verdict

**ENDORSE WITH CHANGES (Significant). Critic gate on D-015 SATISFIED — may move to Accepted.** The mechanism is correct, minimally scoped, honestly verified, and the search-path footgun is closed for the right reason (confirmed against Postgres semantics, not just a passing test). It is a two-way door that nonetheless deserved — and received — one-way-door scrutiny because it is the sanctioned exception to the isolation model.

**Non-optional changes (both forward specs on unbuilt tasks; neither edits `0002`):**
1. **[P1-04] Close the enumeration timing oracle.** On any auth failure — tenant not found, user not found, or wrong password — perform a dummy constant-time argon2id verify against a fixed decoy hash and return a single indistinguishable error. Record this against the P1-04 row now, while it costs a sentence.
2. **[P1-10] Assert the definer hinge, not just the role attribute.** Add to the isolation suite: the two resolver functions are `SECURITY DEFINER`, owned by a BYPASSRLS role (expected `grovyn_migrator`), and carry `EXECUTE` for `grovyn_app` only (no `PUBLIC`). This catches owner drift if a migration is ever run as superuser (§7.3).

**Minor (no gate impact):** rate-limit unauthenticated slug probing at the edge, since `resolve_tenant_by_slug` is a sanctioned tenant-existence/branding oracle by design.

*Objection I tried and why it fails:* "Block — returning `password_hash` from a pre-context, unscoped-by-construction function widens the auth attack surface on the tenancy chokepoint." It fails because (a) returning the hash is the only workable place to do argon2id verification and the hash is not the secret, (b) the function is reachable only via `EXECUTE` by `grovyn_app` and yields one row per exact-key call — strictly narrower than the role alternative, and (c) the genuine residual risk (timing enumeration) lives in the *unbuilt* P1-04 verify layer, is a one-sentence forward spec, and commits no data or schema. Significant-and-required, not Blocking.

**Does anything block S2/S3 of P1-02?** No. S2 (`set_config` bound-parameter context middleware) and S3 (runtime `grovyn_app` pool, no migrator fallback) are independent of the resolver-function choice and may proceed now. The only cross-link is that S4's security-engineer pass should confirm change 1 is scheduled for P1-04 and change 2 for P1-10 — neither gates S2/S3 starting.

*Same-model self-review flagged throughout — this resolves a gap in my own CRITIQUE 016 recommendation; see the header and §B.5.*
